## Ragged row projections: rejected for promotion

The parent already shards large, TP-divisible pool/unpool projections along M, retaining the entire K reduction. Nondivisible M falls back to replicated GEMM. `ragged_screen.py` implements balanced and tail-only partitions, reconstructs all eight rank outputs, checks gather packing, and replays a captured graph after changing the input. It retains BF16 input/weight/output, full K, independent seeds, random/cancellation/magnitude/integer fixtures, alternating timings and a duplicate baseline.

`ragged_pilot.json` and `ragged_tail_holdout.json` are completed RTX3050 runs. The native BF16 and FP32-then-BF16 alternatives are **not universally exact**: M513 unpool and M3011–3013 pool change results. Native pool differences at M3012 exceed 3.3 million elements; requesting FP32 output reduces, but does not eliminate, mismatches. M751/753/755 passed both projection directions across four input styles in the holdout; this is not a permissible workload-specific eligibility rule and is not an algorithm-proof on Hopper. M1/4/16 dispatch remains outside the proposed >=512 guard.

An additional applicability gate rejects the apparent headline gain. `graph_applicability.py` extracts and executes the pinned bucket generator. Every default prefill bucket >=512 is divisible by TP8. Raw753,3012,16383 pad to768,3072,16384; the parent already takes row sharding at these graph shapes. Scored startup confirms target prefill graph capture (15.56GB,151.72s). Ragged improvement is restricted to eager fallback, whose actual frequency is unknown. Stored startup server arguments are truncated, so default bucket inference is explicitly distinguished from a full runtime trace.

Per-rank timing excludes TP8 transport and is not serving latency. A ring all-gather sends `7*ceil(M/8)*N*2` bytes/rank and requires `8*ceil(M/8)*N*2` bytes of gather storage. At M753, pool/unpool send 5,447,680/10,895,360 bytes per rank. Any distributed benefit must pay this traffic plus staging and launch costs, versus native replicated computation; it cannot be reported as an eightfold gain. Larger exactness failures and graph applicability make an H200 quota check unjustified now.

Timestamped downloaded primary records and checksums are in `source_manifest.json` and `sources/`. They include release metadata and exact merged commits, rather than assuming every announcement is available in the pinned runtime.

- [TensorRT-LLM v1.4.0rc4](https://github.com/NVIDIA/TensorRT-LLM/releases/tag/v1.4.0rc4), released November18. [Muse serving PR21049](https://github.com/NVIDIA/TensorRT-LLM/pull/21049) adds parsers/native-tool integration rather than a new prefill kernel. [PR21308](https://github.com/NVIDIA/TensorRT-LLM/pull/21308) reuses append/fork tokenization and prompt bookkeeping; its reported TTFT also includes PR20815 and must not be attributed to one change. [PR20848](https://github.com/NVIDIA/TensorRT-LLM/pull/20848) reduces host metadata work, with much larger gains under many CPU threads. [DWDP PR21012](https://github.com/NVIDIA/TensorRT-LLM/pull/21012) currently targets Kimi K3 context serving and excludes graph/speculative execution. [AR tuning PR20241](https://github.com/NVIDIA/TensorRT-LLM/pull/20241) extends bucket coverage without a directly usable Muse benchmark.
- [SGLang Muse cookbook](https://github.com/sgl-project/sglang/blob/main/docs/cookbook/autoregressive/Meta/MuseSparkOpen.mdx) exposes prefill sequence parallelism with MegaMoE only on Blackwell. H200 needs a different exact backend and collective validation.
- [vLLM Muse optimization tracker64632](https://github.com/vllm-project/vllm/issues/64632) separates GB300 decode, MegaMoE and AMD sequence-parallel changes. Similar mechanisms are already present in the parent or previous-day experiments; none is an unqualified drop-in H200 speedup.
- Latest snapshots of LMDeploy, LightLLM, FastDeploy and Dynamo were checked. Partial-prefix block reuse offers little against this parent's page-size1 cache; disaggregated transfers/router topology require resources outside fixed TP8/EP8. New lower-precision paths do not meet unchanged precision requirements.
- [SSEngine](https://github.com/SyFI-ServingStudio/SSEngine-GLM5.3-Flash) snapshot identifies prefill-focused, one-output-token evaluation on a different model/hardware topology. Its result cannot substitute for scored multi-turn decode serving.

The strongest prior sources are not counted again as new results: target16K dense FFN only1.028–1.041x; native router row shards changed routing; reduce-scatter changed reduction ordering risk; same-batch prefix sharing did not help the long workload. Follow-up investigation is ongoing.

## Graph memory and next structural candidate

The parent already shares graph output storage, weak-references captured intermediates, deduplicates executable graphs, and borrows idle graph scratch. Startup records9064.3MiB borrowable capacity and8386MiB sampling high-water usage. Raising `mem_fraction_static` from the recorded0.85 is constrained by the challenge's +2GiB/GPU rule; no higher-budget configuration is proposed. Root owns same-budget cache redistribution research.

The next source gap is replicated DFlash context projection. `project_target_hidden` executes a complete fullwidth FC on each draft TP rank, even in large prefill. Row sharding the FC and normalized context can save repeated dense work, then an all-gather of8192BF16 values/token feeds each rank's unchanged native KV stage. `dflash_row_screen.py` is a staged exactness screen; it is not yet a promoted source patch. True TP8 transport, native Hopper plan parity and checkpoint-weight validation are required before an H200 gate.

**Corrected ownership veto:** the early proposal to all-gather only1280 finalKV values/token is invalid for the real model. The public configuration has8global KVheads, with a different head on each TP8rank. The screen reconstructed row partitions for one synthetic head's weights and did not establish distributed-head semantics. Its packedKV timing is not a valid TP8 candidate speedup. A valid lower-byte alternative would replicate the8head weight slices once (~140MiB additional weights/rank), project every distinct head on each rank's ownedrows and transpose KV by head owner with all-to-all. That is a separate unqualified design and is not claimed as a result.
