Conditional future hybrid: resident WGS decode + transient large-prefill layouts
2026-11-19; source feasibility only. No integration, compilation, GPU test, or submission performed for this plan.

Conclusion
The storage bridge is feasible in principle because native_package_02 preserves every original FP4 nibble and E4M3 scale byte. Keep only its WGS expert storage resident, execute its native path for qualified decode shapes, and convert the current layer into a single reusable normal-CUTLASS or Humming workspace for large prefill. This is a future hypothesis, conditional on the existing H200 jobs. It is not evidence of a serving gain or of combined numerical correctness.

Direct conversion, without a row-major intermediate
For logical output row n in W13, physical row p = 16*floor((n mod 4096)/8) + (n mod 8) + 8*floor(n/4096); W2 uses p=n. For coefficient column k, the source piece index is (((expert*(N/256)+floor(p/256))*16+floor(k/256))*4+floor((p mod 256)/64)). Within that piece, coefficient word index is 512*floor((k mod 256)/64)+128*floor((p mod 64)/16)+16*(p mod 8)+4*floor((k mod 64)/16)+floor((k mod 8)/2). Decode with serving_code<R,H>, R=(floor(p/8) mod 2)+2*(floor(k/8) mod 2), H=k mod 2. The code is a pure bit permutation; do not multiply/dequantize while converting. The source scale byte is independently addressed by the original _pack indexing. These formulas are source-derived, not yet independently exercised by a new inverse oracle.

A direct converter can write either normal-CUTLASS destinations or the exact inverse destination addresses of grouped_prep._pack_codes/_pack_scales for Humming. Reuse the same physical temporary storage for these mutually exclusive representations. Do not first unpack a full row-major weight copy and then call HummingMethod.transform_humming_layer: that would add full-size temporaries and repeated allocations. Existing native check_pack/qualify_packing receipts verify the forward WGS pack against the donor; they do not qualify this unimplemented reverse bridge.

Ownership and fallback
The simplest shared workspace is both stages: 576 MiB W13 + 288 MiB W2 = 864 MiB, overwritten per layer. It can be the same two buffers already owned by the normal Arena. Normal and Humming views must never be treated as simultaneously valid. A metadata-only Humming facade must be prepared at model load from the original schemas/configuration, retain the original BF16 post scales/locks, and bind stable views into these buffers. A naive fake HopperExperts object will fail the current metadata gates. Review Humming transformation-derived metadata and cached pointer/config ownership explicitly before implementing this facade.

A smaller single 576 MiB stage buffer is also possible, but then the fallback helper must be refactored: convert W13, finish every light/heavy up GEMM, scale/activate, then overwrite with W2 and run every down GEMM. The current split helper assumes both stages available; this is not a drop-in wrapper. Two shared stage buffers minimize semantic changes and still avoid per-layer resident duplication. No 43-way custom-kernel chunking is needed for the incumbent large-prefill fallback itself; it incurs conversion plus its existing complete-M Humming policy. Qualification/build rejection must select this prepared fallback before capture. Never retry after a device execution error.

Graph replay executes captured converter nodes before the consumers, so all layers may share stable workspace addresses only under the proven serialized forward/prefill/decode contract. Do not cache converted contents as a per-layer hit, free/reallocate graph-owned buffers, or retain a second arena per stream. Existing TBO/SBO/PP and stream guards must remain. Multi-model/concurrent execution is outside this proposal. Pre-create descriptors and metadata without model-sized dummy tensors. Extra temporary WGS routing/fixup buffers and allocator/capture pools must enter the global peak budget; the current 1.749 GB qualification estimate cannot simply be inherited by a hybrid.

Math and traffic
Original E2M1/E4M3 group16 bytes and BF16 global scales survive conversion unchanged. Native WGS uses its full-value BF16 coefficient table and serving_scaled's BF16 GEMM-result -> BF16 global-scale rounding. New normal CUTLASS uses quarter-normalized BF16 coefficients and BF16-result times four before the same post scales. The destination bridge must preserve that distinction; copying the WGS coefficient table into the quarter-normalized reader would be wrong. FP32 reduction order also differs. Byte equality of restored weights does not prove WGS/CUTLASS/Humming outputs equal; actual native and grouped model gates remain separate prerequisites.

At 32 experts, N13=8192, N2=4096, K=4096: one full direct repack reads 905,969,664 bytes and writes the same, at least 1,811,939,328 bytes (1.6875 GiB) per layer invocation, before GEMM reads. Both destinations have this same ideal traffic. Across 60 layers that is 108,716,359,680 bytes (~108.7 GB) additional repack traffic per full pass if every layer converts. Access inefficiency can increase it. These are traffic counts, not timing predictions. Converting both stages once and reusing across prefill chunks is essential. Keep proven native decode calls on resident WGS, with no repack there; routing fallbacks for unsupported decode shapes would pay this cost and must be measured separately.
