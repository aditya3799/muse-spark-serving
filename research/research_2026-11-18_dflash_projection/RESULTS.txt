DFlash2 column-sharded context projection | 18 November 2026

Experiment
The working parent scored 1.2363 on the four-load serving frontier, job 317c88a5fd474cd2. candidate.diff adds a DFlash2-only BF16 context projection change on eligible CUDA tensor-parallel configurations. Each rank loads contiguous output features, computes their complete dot products, rounds to BF16, and gathers the features before the existing RMS normalization. Stock target verification still executes. A rank-zero startup log identifies activation. The independent mixed-chunk investigation is job b2fa80590214468b.

Reproduce
Run build.py with Python 3.10 or newer and Git in PATH. It verifies the scored parent hash and reads the pinned DFlash source via Git. For the arithmetic and timing benchmark run verify_transport.py gpu dflash.py ../sglang gpu_new.json under PyTorch 2.14.1 CUDA. For the two-rank loader/ordering check use OMP_NUM_THREADS=1 python -m torch.distributed.run --standalone --nproc-per-node=2 verify_transport.py distributed dflash.py ../sglang distributed_new.json. Run prefill_graph.py and precision_compare.py with the same CUDA environment for the prefill and arithmetic comparisons. Paths assume this folder as the working directory.

Results
The complete patch passes git apply --cached --check --whitespace=error on a temporary index populated from 297e54fd105e974cdf401e5b4d20253a22c16f90. Its SHA256 is 340cf16482660959982e6d10182db1b83d3e7f8a13e8c6e07008a84a8da52ff73.
The two-process fixture passed 16 checks per rank covering three checkpoint names, rank-local weights, restored feature order, normalized integer-valued outputs and malformed weights. Both processes use one RTX 3050 with Gloo over CPU for interprocess transport. Group setup and RMSNorm are fixtures. An initial CPU-only attempt reached a CUDA-only torch.mm overload and was replaced with the GPU test.
On the RTX 3050, paired projection timing at 8,32,128,256,753,1024 rows gave 7.48,7.33,5.88,8.61,7.51,7.66x, respectively. At 4096,8192,16384 rows the ratios were 8.42,8.69,8.38x. These compare full GEMM time with one output shard and exclude inter-rank communication, reordering, normalization and serving. A separate 128-row CUDA graph replayed five changed inputs exactly against eager candidate arithmetic. Stock and candidate floating point outputs differ. Across the first six shapes, about 47-64% of elements matched stock bitwise. Sampled comparison with a double-precision oracle favored FP32 output in the larger prefill tests. This does not establish model-level token agreement.
At 16384 rows the local projection above live inputs/weights allocated a peak 96 MiB. The full gathered output is 256 MiB, and the pinned all_gather may make a second full-size buffer to restore feature order. Weight storage for this layer falls from 640 to 80 MiB per rank at TP8. These are component figures; total-device memory, NCCL time and H200 token agreement remain to be measured.
For scale, using 8x as an illustrative component speedup, Amdahl's law requires the projection to account for 43.6% of current time to move 1.2363x to 2x, or 57.8% to reach 2.5x. This calculation assumes fixed work and ignores gather overhead. No measured H200 profile establishes those shares, and the judge scores an interpolated throughput frontier.
The most informative next H200 experiment is 16 users, the packaged patch, humming as the only flag. Compare with the matched parent/control only when workload and measurement protocol align. Confirm the activation line, correctness, later turns, acceptance, TTFT, peak memory, and throughput. Treat approximate single-load checks separately from scored four-load frontier results.

Alternative partition axis
axis_compare.py gives each rank one eighth of the token rows and all of the BF16 weights, then gathers rows. It measured bitwise equality to stock on all live rows at M=753,1024,4096,16384 in one seeded local trial. At M=8,32,128,256 exact fractions fell to 48-58%. At M=8 local row compute took 5.39 ms versus 0.78 ms feature compute plus 0.07 ms reorder. At M=16384 the same comparison was 94.91 ms versus 92.59+4.57 ms. These timings exclude communications; the row partition needs the full 640 MiB weight on each rank. The measured small-row penalty and equal large-row compute times favor retaining feature sharding in the candidate already sent. Actual H200 performance and parity by shape may differ.

Expert-placement sensitivity
placement_bounds.py tests up to eight disjoint whole-expert swaps. Each of eight ranks keeps exactly 32 unique experts. The planner fits 20 earlier synthetic batches and evaluates 40 separate batches with unique top-8 routes per token. The cost is the maximum rank sum of 16-row expert tiles, added across test batches. At 753 tokens, a persistent cluster improved that tile-count proxy by 1.739x. Uniform routing gave 1.000x and shifting the hot cluster gave 1.056x. At 128 tokens the three ratios were 1.347x, 1.000x and 1.034x. These numbers describe a synthetic load-balance model. They do not measure wall time, actual model routing, or the numerical and publication effects of moving weights. They provide no basis for adding an expert-swap policy to the submitted candidate.
