# Causal suffix proposals for the pinned DFlash worker

The tested proposal module is independent of SGLang. `suffix_store.py` supplies CPU and PyTorch reference operations, `suffix_cuda.py` fuses the long-context index, lookup and appends in Triton, and `suffix_routing.py` translates DFlash's existing bonus and KV length into a per-request proposal. All public trajectories and timing inputs stay outside these modules.

## Evidence

CPU and physical GPU qualification used the exact Muse tokenizer, four held-out SWE-smith trajectories and an independent historical substring search. All 258 independent witnesses matched across 280 deliberately hit-enriched probes. Guard tests cover truncation and delayed writes, slot reuse, duplicate updates, forced collisions, invalid anchors, zero- and short-budget rows, invalid token IDs, and cross-boundary continuations. Hits in these probes measure parity. Natural coverage and other public workload measurements are separate.

The GPU measurements used the RTX 3050 Laptop 6 GB, 74,000 confirmed tokens plus small per-row offsets and CUDA events around independent captured lookup and append graphs. Each run changed anchors, epochs' expected frontiers, token IDs and committed counts across 80 steps. It checked every reported hit against the token history and every updated frontier against a separately computed count. The lookup received the current epoch throughout. The benchmark excludes staging test inputs, target verification, packing the target inputs and cache materialization.

The two real windows yielded about 99% and 5–9% proposal hits in these timed portions. An end-to-end serving distribution cannot be estimated from those two windows. Warm 74k-token full-prefix indexing cost roughly 0.26–0.35 ms per request in the large batches. The first Triton compile plus bind took 1.50 s in the cold run. Each 131,072-token, 65,536-bucket index uses 1,048,604 persistent bytes per active request. Outputs, graph capture, kernels, target attention and KV pools have additional memory costs. See `gpu_suffix_timings*.json` for all quantiles and timing details.

In a separate continuous-refill replay across 40 trajectories, using one 32-token batch only when every row has a source gave target-forward count ratios 1.457/1.041/1.010/1.008 at batch sizes 1/4/16/32. A single packed target call with 32-wide copy rows and 8-wide DFlash fallback rows reached 1.457/1.463/1.488/1.482 in the seed-109 replay. These are step counts assuming four commits per neural fallback verify. The experiments do not measure H200 elapsed speed or acceptance by the real Muse target. More independent data and fallback-correlation sensitivities are in the sibling frontier directory.

## SGLang integration boundaries

The inspected source is `297e54fd105e974cdf401e5b4d20253a22c16f90`. The judge uses a fixed trained DFlash width of eight with FA3 for the target and FA4 for the draft.

1. At admission, associate the live request pool slot and a fresh epoch with the request ID. On final prefill only, initialize from the entire actual prompt and target bonus; a chunk or radix-hit suffix alone is insufficient. `scheduler_components/batch_result_processor.py` lines 304–379 show the existing final-vs-middle chunk/retraction guards. An alternative worker-side lifecycle can copy confirmed GPU tokens and the target bonus before `_make_next_draft_input_prefill`. The first successful proposal requires the confirmed-token frontier to equal `batch.seq_lens + 1` and the final token to equal `draft_input.bonus_tokens`. On request reordering, pass slot/epoch keyed by the actual request. On retract or retry, truncate through the checked handle and propagate the freshly returned epoch before new work. A stale operation from the first branch must not mutate the second branch even if they reach the same length. Releasing state must wait for the producing stream.
2. At `dflash_worker_v2.py:2485`, immediately before the fixed neural draft block, query `DFlashCopyRouter.route`. Require a greedy, unconstrained, supported batch, sufficient remaining request and context budgets, and reserved KV slots for every active verify query. Copy rows provide anchor plus 31 known tokens. Neural fallback rows retain the trained eight-token draft. The uniform gate is `routes.all_copy`. Its poor high-concurrency step count motivates a single mixed-width target pass. Running both cohorts independently doubles target launches on mixed steps, and performing the full neural draft whenever there is any miss reduces the draft saving.
3. `dflash_info_v2.py:142–149` reserves twice the fixed draft width for overlapped decode. Its existing reservation is 16, already less than one width-32 verify. Keep trained draft width eight, split out the maximum target window with a 64-token concurrent reservation, guard available context and propagate the corresponding reservation into schedule accounting and safe KV mapping. Page-aligned allocation can change the actual footprint. Handle retraction and priority pressure through the scheduler.
4. Reuse DSpark's `BuildRaggedVerifyWindow` and `dspark_components/dspark_verify.py:425–479` packed target admission contract. Reserve and translate the 32-wide per-row virtual window, pass its `window_index` to `DFlashVerifyInput.kv_loc_cols` so each backend receives addresses in its own space. The output stride and the packed query starts are independent. Feed `GreedyCommit.verify` the **original live** `layout.qo_indptr_device` with B+1 elements and a final entry equal to the actual total. The B-element `extend_start_loc` omits the final boundary. The padded capture layout can artificially enlarge the last live row, so it cannot establish a commit boundary.
5. `spec_info.py:160` enables compact ragged verify graphs for DSpark alone. The target graph runner checks this in `model_executor/runner/decode_cuda_graph_runner.py:397`, allocates per-tier buffers and performs graph admission at line 927. FA3 eager target metadata at `layers/attention/flashattention_backend.py:1038` supports per-row lengths. Without host lengths its maximum query length falls back to the configured draft width. FA3 graph capture at line 2828 uses that same fixed width; replay at line 3173 refreshes query pointers without widening this upper bound. Capture the maximum target query and choose a tier/padding distribution which keeps real and ghost rows inside the bound. A backend-specific capability gate must preserve stock behavior where unsupported. The DeepSeek `compute_target_verify_graph_key` is not the active FA3 backend admission.
6. Retain the original target argmax after TP synchronization and all normal greedy constraints. `dflash_worker_v2.py:2878` runs the actual target and `:2926` accepts the chain. The existing fixed reshape at `:2228` cannot consume packed data. Use the packed verifier's row-specific source and validity mask. `GenerationBatchResult.speculative_output_stride=32` is already supported by `scheduler_components/batch_result_processor.py:87` and permits rectangular output for overlap/scheduler consumers.
7. `dflash_worker_v2.py:2981–2991` currently reshapes target hidden with the neural block width and writes committed verify inputs to draft KV. Use actual packed hidden source indices and the draft reader's translated physical or virtual KV slots. Valid inputs are the old bonus anchor and the matched draft prefix. The next bonus is emitted but its KV is first materialized the following step. Append only newly emitted accepted tokens plus next bonus to the suffix store. A fast commit helper alone does not complete the pinned draft KV step.

A fully integrated 8×H200-equivalent target/draft launch, TP/EP agreement, graph bucket checks, clean multi-turn parity, peak memory and H200 end-to-end timing are outstanding. The measured component results do not establish a 1.8× serving speedup.
