# Standalone local timing summary for the full-work projection

The fixed pilot selection ran at 1.238× full-width throughput at 256 rows and 1.051× at 128 rows on independent inputs and weights. The candidate ran the same 40960-dimensional inner product for all 8192 output channels on one physical GPU. Local and distributed output sharding played no part in these measurements. The 8-, 32-, 753-, 768- and 3072-row results were near parity. At 16,384 rows one complete 793 ms native call and one complete 797 ms candidate call matched in all 134,217,728 output elements.

The search sampled legal runtime vendor tile, workspace and split-K configurations. Candidate survivors reproduced native BF16 output on full random and mirrored K-block cancellation fixtures before timing. The best median from three timing samples among qualifying candidates was frozen. Each confirmation used twelve paired forward/reverse samples per arm, all output bits over four changing inputs, a new weight seed, and a separate cancellation fixture. The native control executed the original PyTorch call. Shuffling and reversing the order inside a pair preserved per-arm order in the reward receipt.

The observed host selection times per shape were 3.36 s, 2.74 s, 2.09 s, 4.10 s and 9.98 s for 8, 32, 128, 256 and 753 rows respectively. At the held-out median differential, the startup cost at 256 rows would take approximately 1,530 repeated calls of that shape to recover. The corresponding threshold at 128 rows is about 6,300 calls. These estimates exclude process cold start, calibration data creation, and distribution. Hot-path full-width scratch for the 128- and 256-row winning configurations was 128 and 256 bytes. The discovery process evaluated alternatives with up to 32 MiB temporary workspace.

## Coupled target and draft confirmation

The candidate and two native arms replayed the scored parent's five target residual taps, the full BF16 projection, the pinned FlashInfer 0.7.2 CUDA RMSNorm, the dense draft KV projection, and cache writes for all five layers. Only the full-width projection implementation changed. The full-width plan was fixed from a different seed before either coupled run. Each seed/replay changed all five residual snapshots and sparse physical cache slots. The two strata used partial and full block acceptance. The last iteration compared entire backing pools. Each seed inspected 347,494,400 cached BF16 values per arm in addition to all FC, normalized and dense-KV outputs. All comparisons passed.

Equal-weight paired wall-clock gain was 1.0802× (95% interval 1.0533–1.1154) on the pilot and 1.0689× (1.0550–1.0852) on the held-out seed. The 32-request held-out cases improved from 14.79 to 11.91 ms for partial acceptance and from 14.84 to 11.92 ms for full acceptance. Results at low concurrency were near parity or mixed. This does not time the transformer layers, the complete speculative cycle, eight-device collectives, model loading, or full serving. ## Runtime activation and deployment limits

[full_runtime.py](full_runtime.py) provides an inference-only full-width tuner that accepts any eligible contiguous BF16 ordinary bias-free Linear, input geometry and GPU supported by the runtime vendor library. Default strict mode computes the original projection and uses native bits on any divergence. Empirical mode skips that shadow and trusts the runtime-selected plan. The source binds everything needed for CUDA launch to the actual call and can reject unknown shapes, dtypes, weights, streams, math policy and workspace. The standalone adapter requires pre-registration after checkpoint loading. Production warmup can be integrated after DFlashWorkerV2.init_cuda_graphs with actual configured capture geometries; project_target_hidden should keep the same hidden_norm and native-layer fallback. A complete scored SGLang patch is not promoted by these local results.

The local full-width candidate has unchanged tensor precision and operation count. NVIDIA does not guarantee bitwise identity across algorithm changes. Finite validation, including the cancellation fixtures and the downstream cache tests, is strong local evidence. An unconditional runtime check runs both GEMMs and gives up the intended speed benefit. H200/driver/CUDA-specific plan selection, GPU graph lifecycle, scheduler-stream binding and the qualifier's cold-start cost must be measured on the deployment stack. Published score rules impose both a per-load TTFT limit and an additional peak memory limit. Inline tuning on the first user request can consume either budget. The safe startup qualification should take place before admission and must retain native fallback when compilation, calibration or available memory is insufficient. No scored run was issued.
