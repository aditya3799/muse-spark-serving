# One Humming coefficient bank for both engines

NVIDIA's CuTe reordering atom with four MMA atoms extended across the output-feature dimension produces exactly Humming's frozen Hopper WGMMA weight layout. The C++ enumerator ran the official CUTLASS helper and compared every nibble position in 128×64 and 256×128 packed matrices. It matched all 40,960 addresses, including transitions between warp, N and K tiles. The upstream example's default one-atom variant matched only 128 of 8,192 addresses in the first test. The four-N atom matched only half the addresses for the alternate HMMA mini-block ordering, so the native grouped adapter checks for WGMMA. [Exact target and negative controls](atom_addresses.json) [Pinned example 69](https://github.com/NVIDIA/cutlass/blob/cd9d8a7d612b6b9ad0f1b698925e31243e828629/examples/69_hopper_mixed_dtype_grouped_gemm/69_hopper_int4_bf16_grouped_gemm.cu#L120-L128)

For native WGMMA, the four-N CuTe atom has output-feature shape (8,2,4) with nibble strides (128,1,8), and K shape (2,4,2) with nibble strides (4,32,2). Each additional 64-row N tile advances 1,024 nibbles. Each K16 tile advances 16N nibbles. The original 768 MiB/rank/layer of coefficient bytes can therefore be consumed from the same addresses on both branches. The 96 MiB of group-16 FP8 scales is the remaining layout difference. [Embedded CuTe type](humming_atom.hpp)

Two adapter modes retain one resident copy of the coefficients and scales. Both require a true Hopper FFN gate for the grouped GEMM.

| Stored scales | Ordinary Humming small-row path | Grouped large-row prefill | Extra conversion storage |
|---|---|---|---|
| Original native | Exact unchanged scored Humming | Repack only scales in each phase | One shared 64 MiB per-stream W13 scratch, reused by 32 MiB W2. Logical read/write traffic is 192 MiB per layer. |
| Four-byte words | Change only the scale load in the ordinary non-mbarrier kernel. Other configs selectively restore the active native scales. The original weight loader remains in place. | Direct shared coefficient and scale pointers | No grouped conversion scratch. A 64 MiB independent per-stream native fallback suffices for unsupported small-row configurations. Startup transient is 96 MiB per layer. |

Both policies keep total weight and scale storage at 864 MiB/rank/layer, 50.625 GiB across 60 layers. Each stream additionally needs the grouped activation/padding workspace and CUTLASS descriptors previously itemized. The Python adapter provisions one maximum activation workspace and slices it for smaller graph buckets. The gated grouped capture remains hardware-unverified. [Adapter](group_runtime.py) [Scales-only installation and active fallback](shared_scales.py)

The earlier full-layout direct small-row loaders completed real graph A/B. The scalar approach measured 0.718–0.784× and the aligned-vector approach 0.793–0.809× after duplicate-control centering. Every live raw W2 and finalized BF16 value matched. These results apply to changing both weight and scale access. They supplied a reason to retain the original weight access while changing only the scale reader. The two previously tested external full-repack seeds measured 0.276–0.449×. Public UW-SyFI captured GLM-5.3 routes yielded median 5, 11 and 19 active experts per logical rank for sequential windows of 8, 32 and 128 routed rows. This corresponds to 270, 594 and 1,026 MiB of full restore traffic at the median, or 30, 66 and 114 MiB for scale-only selective restoration. Window grouping does not reconstruct request membership. The captures belong to GLM, and serving-time Muse expert IDs remain unavailable. The frozen Muse kernel-task fixture’s busiest rank at M128 had 17 and 3 active experts in the normal and skewed samples.
