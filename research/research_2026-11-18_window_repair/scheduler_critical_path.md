# When a scheduler change shortens a DFlash round

The pinned overlap loop polls for arrivals, chooses the next batch and submits its model work from the same host thread. It then processes the previous batch. A GPU result readback normally uses a separate copy stream gated behind the producing forward. In ordinary overlap, the host can launch the current step before waiting for the previous result’s copy. Grammar and selected consecutive-prefill cases can require processing that result first. A scheduler GPU write is gated by a shared-read event when the backend supplies one, otherwise by a forward-stream barrier. The two-slot batch-record ring merely retains Python/tensor references; it inserts no GPU or host barrier. [Overlap loop](https://github.com/sgl-project/sglang/blob/297e54fd105e974cdf401e5b4d20253a22c16f90/python/sglang/srt/managers/scheduler.py#L2061-L2158) · [Result copy](https://github.com/sgl-project/sglang/blob/297e54fd105e974cdf401e5b4d20253a22c16f90/python/sglang/srt/managers/scheduler.py#L5018-L5042)

The SSEngine-inspired receive patch changes the non-attention-DP branch when the TP group has a same-host MessageQueue broadcaster with no remote subscriber port. All ranks exchange a boolean there. An empty poll returns its empty payload at this boundary. Nonempty arrivals continue through the existing Gloo object broadcast. Its original receive-wrapper, MM, cache consensus and result-consumption work still run. For a continuing request, the exposed delta in a simple issue-limited round is the decrease in max(G, H), where G is time until previous GPU work permits the next useful launch, and H is time at which the slowest required TP rank has enqueued the needed inputs. A request arriving to an idle GPU can see a larger fraction of the host change; arrivals also incur the new nonempty flag. The limited local eight-rank CPU tests include a four-int Gloo minimum. At one arrival in eight the medians saved around 0.81 and 0.93 ms per receive iteration across independent seeds. H200 queue depth, CPU lag, topology, poll mix and rank skew were unmeasured. A DFlash decode round publishes next sequence lengths immediately after target acceptance and before draft KV append. FutureMap resolves those lengths on the next scheduled forward. In the normal CUDA no-host-mirror path, waiting for publish_ready orders GPU work on the schedule stream; the forward stream then waits for schedule writes. If either DFlash attention backend requires a host mirror, the private D2H stream waits for the publish event and synchronizes on the host. TBO forces the legacy CPU mirror. Plain FA3 opts out unless it uses a sharded KV pool. Consequently faster polling can fall entirely inside an outstanding CPU mirror wait or existing GPU backlog. The DSpark confidence ring is separately gated on DSpark and is ineligible for DFlash2. The separate deferred target graph-preparation patch keeps one complete registry fill and attention-metadata setup per eligible target verify. The original worker performs this during prepare_for_verify, then target replay enters load_batch again with skip_attn_backend_init set and refreshes input IDs, positions, key/variant state and any branch-specific extras. DFlash does not qualify for the DSpark prefilled-input identity shortcut. The candidate defers the full pass to normal target replay, leaving eager/non-CUDA handling and already deferred attention-DP behavior in place. Its duplicate GPU copies sit on the same stream before the target graph can run, so shortening them can advance that target graph. The CPU work of the removed second pass may already overlap outstanding draft GPU kernels; neither the attention plan nor model graph is removed. Per-step exposure needs the time to the next target launch on the critical rank. A validating trace would place host monotonic stamps at poll completion and next target replay issue, one target-GPU event before the remaining full metadata fill, and paired CUDA events around the target graph. It would distinguish idle, late-arrival, steady full-overlap and forced synchronization rounds, with per-rank slowest arrivals and copy/mirror mode. The local polling study cannot identify those fractions of an H200 serving round.
