REQUEST-LOCAL PROMPT LOOKUP RESEARCH - ROUND5

This lane implements proposals from only the current request's confirmed token history. It does not change the active server. Every committed token still comes through target verification. There is no measured serving speedup or real-workload acceptance estimate.

CPU CONTRACT AND FIXED8 WORKER OVERLAY
request_lookup.py provides versioned own-request history, bounded occurrence indexing and explicit source-span provenance. test_request_lookup.py executes extracted existing DFlash CPU acceptance/commit functions for every rejection position at widths2/4/8/16/32, and compares to an independent causal serial-target oracle. Synthetic model tokens are not Muse output.
lookup_runtime.py and lookup_default_off.diff implement a default-off fixed8 injection point. It preserves stock embeddings, compact draft-cache reconstruction and KV translator binding, then can skip the draft forward/sampler for all-hit batches. Mixed-hit batches still run the full draft and replace only matched request rows. Target verification, acceptance and target-hidden-to-draft-KV append remain byte-for-byte unchanged outside the proposal branch.
The first independent review found that equal history length/anchor did not establish request identity. The runtime now checks ordered actual batch request IDs and lifecycle epochs; regressions cover foreign same-anchor/same-length snapshots and stale epochs. CPU source-fragment tests pass; whole-worker behavior remains unexecuted. Runtime TP>1 bypasses this hook until real rank-coherent control/payload handling is qualified. A snapshot provider is not installed in the scheduler.

OVERLAP BOTTLENECK AND RESIDENT HISTORY
Stock CPU metadata intentionally lags one step. Its count-only callback cannot reconstruct current token history. The CPU adapter performs explicit anchor/length readbacks and falls back if history is stale; these costs and lost opportunities preclude a gain claim. Rebuilding an index on every changed host history is also an unresolved cost. SOURCE_INTEGRATION_FINDINGS.json records the exact source constraints.
resident_lookup.py is a separate GPU component that keeps target-confirmed token IDs on device, finds a fixed7-token continuation from the same request, and appends the verified emission including the new bonus. This token-history frontier is DIFFERENT from attention KV: KV appends the old anchor plus accepted proposals and excludes the new bonus.
The first native GPU run and second epoch/bounds-hardening run passed. Tests execute actual existing DFlash CUDA acceptance, changed lookup and append CUDA graphs, independent CPU source matching, unique slot permutations, overflow poisoning, EOS exclusion, stale slot epochs and invalid slot bounds. The second run's peak torch allocation was1,553,920bytes; reserved23,068,672bytes. Both are component allocations, not total device-memory compliance measures.
The latest synthetic B4x74176 lookup component averaged about59.7microseconds over40 CUDA-event iterations on RTX3050. This excludes CPU decision/readback, model forwards, score/acceptance quality, TP8 communication, cache integration and server overhead. It is neither an H200 forecast nor a baseline speedup. The earlier55.3microsecond observation is preserved separately, not selected as best.

IMPORTANT HOLDS
GPU-history component is not wired to serving. Production use requires actual request admission/retraction/finish epochs, unique slots, stream-ordered reset/bind/lookup/append, prefix/anchor agreement, finish/output-budget handling and all-rank control agreement before skipping collectives. Mutable tensor access can bypass the prototype binder; caller ownership remains a required contract. Valid epoch alone does not establish the correct current frontier. Supported EOS-list length is at most2 and fixed output width8; unsupported states need stock fallback.
The existing GPU and CPU lookup policies are intentionally different experimental implementations: CPU uses bounded occurrences and can return short continuations; resident GPU scans for a full7-token continuation. No claim of policy equivalence or matched acceptance is made.
Token table memory is small in these fixtures but scales with request/context capacity and must share the +2GB per-GPU total-device budget with every other candidate.

FRONTIER HARDENING ADDENDUM
resident_frontier_lookup.py is a separately preserved variant of the qualified V2. It requires the current target pre-verify prefix length and anchor on GPU in addition to the request epoch. Lookup rejects a mismatched frontier. Append checks the same pre-verify frontier, so a duplicate replay cannot append the output a second time or disable an already advanced valid request. The frontier_gpu_01 delta passed12 changed valid-then-duplicate graph cycles, wrong-anchor and matched-permutation checks, using21,504bytes peak allocation. Its prescribed output tokens are a fixture; native acceptance qualification remains in the separate V2 receipt.
The exact expected frontier must be bound BEFORE the associated verify/append, in matching request-row order, on a serialized serving stream. Wiring that lifecycle into actual scheduler/TP8 remains unimplemented. This addendum closes a component guard gap, not whole-serving integration.
