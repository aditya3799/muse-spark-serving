Candidate_v2 integration and fusion follow-up review

Verdict: no integration blocker found in this fresh CPU-only audit. This is the implementation author's source/artifact review; projection provides a separate independent review. INTEGRATION_REVIEW.json records all verified hashes.

The fp4 dispatcher is byte-identical to frozen v1. The quantization file changes only one import, removal of the clamp/int64 scale-index setup, and two scale calls. New module lives at python/sglang/kernels/ops/moe/muse_spark_humming_scale.py. Guards inspect tensor metadata only and return before launching for zero rows. The scaling kernel branches on each current device ID before loading either output or scale. The serving lookup produces -1 or a local expert index; positive IDs outside the scale table are outside this caller contract. Existing activation and finalization ignore inactive routes, so unchanged uninitialized invalid rows remain unobserved.

Source hashes match the exact exported-helper run (12 eager cases,36 graph replays,session51659 exit0). The exported kernel AST equals the kernel used by the exhaustive finite-BF16 proof:65,280 patterns x14 scales =913,920 products, plus four changed-ID graph modes, all int16-identical to torch multiplication. The exported wrapper adds metadata guards only. Frozen v1 hashes remain unchanged. H200 execution/full-serving import are still unverified; four offline Humming cubins do not cover this new Triton kernel.

Fusion assessment: a bounded follow-up is worthwhile only as an incremental optimization after routing/tile study, not as evidence for1.6x. V2 already removes the large inactive traffic. Its allremote residual versus stock is about4.1us atM8 and3.1us atM128; these differences include other backend overhead and are not a measured scaling-kernel cost. There is no profiling evidence yet that two remaining scaling launches dominate active routes.

Preferred first experiment: fuse only the down scale into the existing Triton finalizer. At every live output load, compute FP32(output_BF16)*FP32(expert_scale_BF16), cast back to BF16, then promote to FP32 before the unchanged norm/score operations. Do this in all three finalizer kernels: monolithic post_expert_norm_weighted_sum, small-batch inv_rms, and tiled_combine. The latter two each need the identical round-back because each independently loads the original GEMM output. Gate deferral only when the recognized fused-norm path is used; retain explicit scaling for arbitrary post_expert_norm fallback. Never algebraically cancel scale through RMSNorm: BF16 rounding and nonzero epsilon make that invalid.

This removes one launch and one BF16 read/write pass, saving4*R*H bytes forR live routes (2MiB atM128/topk8/EP8 uniform expectation,H4096;16MiB for a fully local hot rank). Norm reduction order and per-slot accumulation can remain unchanged. Required decisive proof: exact final-output equality against v2 across changing scales/norms/routes, inactive->active graph transitions, both monolithic and small-batch two-phase paths; then paired stage/component timings with noise controls.

SiLU fusion can save a second launch and8*R*I bytes (4MiB uniform expectation or32MiB hot rank at the same geometry). However stock activation.cuh:25-28 uses float x/(1+expf(-x)), compiled with --use_fast_math (jit/utils/arch.py:201), and filtered vector CUDA execution. A naive Triton sigmoid substitution changes approximation/rounding. Prefer a future optional scale input to the existing eligible CUDA activation kernel with explicit BF16 conversion before calling the unchanged apply_activation_f32, if profiling justifies the extra compile/review scope. Do not implement both fusions at once.

No fusion code was implemented, no GPU/compiler was launched, and no frozen export was modified during this review.
